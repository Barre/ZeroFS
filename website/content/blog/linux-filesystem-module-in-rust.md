<p class="lede rv">ZeroFS now has a native kernel client: an out-of-tree Linux filesystem module written in Rust that is a port of the userspace client, with a small amount of C for the <a href="https://docs.kernel.org/filesystems/netfs_library.html">netfslib</a> helpers the Rust bindings cannot reach yet. It registers <code>zerofs</code> with VFS, moves file data through netfslib, and speaks the private <a href="https://www.zerofs.net/docs/9p-extensions"><code>9P2000.L.Z</code></a> dialect itself over TCP or a Unix socket.</p>

<h2 class="rv" id="from-userspace-to-the-kernel">From userspace to the kernel</h2>
<p class="rv">With <code>zerofs mount</code>, every operation the page cache cannot answer leaves the kernel through <code>/dev/fuse</code>, gets turned into a <code>9P2000.L.Z</code> request by the bundled userspace client, and re-enters the kernel as a socket write to the server. The reply makes the same trip in reverse. That detour compounds, because a strongly consistent network filesystem is chatty: writing one file is a walk to the file, an open, a <code>stat</code>, the writes, perhaps an <code>fsync</code>, then a close, and most of those cannot be answered from cache without weakening consistency. Each one pays the round trip through userspace. The client is also an ordinary process, and the mount fails if it dies.</p>
<p class="rv">Linux v9fs removes the userspace hop but speaks standard <code>9P2000.L</code>. It cannot use ZeroFS metadata operations, does not reconnect after a server restart or failover, and has no notion of a leader/standby pair.</p>

<h2 class="rv" id="rust-in-the-kernel">Rust in the kernel</h2>
<p class="rv">Linux 6.18 ships enough in-tree Rust for the everyday parts of a module: the <code>module!</code> entry point, allocation with explicit GFP flags, mutexes, spinlocks, condition variables whose waits report pending signals, errno-based errors, kernel strings, credentials, and iov iterators; code written against them reads like ordinary Rust.</p>
<p class="rv">There is no in-tree abstraction for VFS itself yet. The module declares its <code>file_system_type</code>, <code>super_operations</code>, <code>inode_operations</code>, and <code>address_space_operations</code> by filling the raw C structs from the generated bindings in <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/vfs.rs"><code>vfs.rs</code></a>, and each callback in those tables is an <code>extern "C"</code> function that rebuilds typed Rust state from raw kernel pointers before doing anything else. Sockets and threads likewise go through the raw bindings: <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/transport.rs"><code>transport.rs</code></a> calls <code>sock_create_kern</code>, <code>kernel_sendmsg</code>, and <code>kernel_recvmsg</code> directly, and <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/client/mod.rs"><code>client/mod.rs</code></a> starts the connection task as a kthread with <code>kthread_create_on_node</code>. <code>kernel::error::code</code> declares constants for most errnos but not <code>ESTALE</code> on every kernel, so <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/zerofs_main.rs"><code>zerofs_main.rs</code></a> pulls it from the raw bindings with a two-line macro.</p>
<p class="rv">Nearly all of the module's <code>unsafe</code> sits in that glue; the protocol implementation has none at all, and the session logic almost none. The module implements most of what VFS asks of a filesystem: mounting, lookup, attribute reads and changes, file and directory creation, rename and unlink, hard and symbolic links, device nodes and fifos, persistent opens, <code>atomic_open</code>, directory iteration, buffered reads, dirty-folio writeback and writable <code>mmap</code>, direct I/O, <code>fallocate</code>, <code>SEEK_DATA</code> and <code>SEEK_HOLE</code>, POSIX record locks and <code>flock</code>, <code>fsync</code>, and <code>statfs</code> against the remote filesystem.</p>

<h2 class="rv" id="the-c-that-remains">The C that remains</h2>
<p class="rv">The module is not quite pure Rust due to the use of netfslib. The Rust-for-Linux bindings do not cover it yet, so the build runs bindgen over the target kernel's <code>&lt;linux/netfs.h&gt;</code>. Bindgen cannot generate calls to static inline functions, though, and much of netfslib's helper API is exactly that; those helpers are recompiled in two C files, <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/netfs/compat_helpers.c"><code>netfs/compat_helpers.c</code></a> and <a href="https://github.com/Barre/ZeroFS/blob/main/kernel/vfs/compat_helpers.c"><code>vfs/compat_helpers.c</code></a>, fewer than 250 lines between them, which also alias the fields that newer headers rename or make private.</p>
<p class="rv">The same machinery sets the version floor. 6.18 is the first kernel whose in-tree Rust support covers what the module needs, and past it there is no version check anywhere in the build: bindgen and a set of struct-layout assertions run against the exact kernel tree being targeted, and a tree that cannot support the module fails to compile.</p>

<h2 class="rv" id="buffered-io-through-netfslib">Buffered I/O through netfslib</h2>
<p class="rv">Netfslib is the kernel's shared I/O layer for network filesystems. It handles readahead, dirty-folio writeback, writable <code>mmap</code>, and direct I/O, and asks the filesystem only to move bytes: the module implements netfslib's request operations and turns each subrequest into <code>9P2000.L.Z</code> reads and writes. The mount negotiates a message size of up to 10 MiB, so a large readahead or writeback batch can travel as a single request. Caching policy is a mount option: <code>consistency=relaxed</code>, the default, allows one second of caching, while <code>consistency=strict</code> revalidates on the server and does unbuffered I/O.</p>

<h2 class="rv" id="one-connection-many-callers">One connection, many callers</h2>
<p class="rv">Each mount holds one connection to the server. Requests carry 16-bit tags, and replies can come back in any order. A VFS caller serializes its request, writes it to the socket, and waits on its own tag; a single connection task reads the stream, reassembles complete replies, and wakes whichever caller was waiting on that tag.</p>

<h2 class="rv" id="kernels-without-rust">Kernels without Rust</h2>
<p class="rv">Linux has no stable module ABI, so a module is always built for one exact kernel release, configuration, flavor, and architecture. For a C module that means having the right headers. A Rust module needs more: a kernel built with <code>CONFIG_RUST=y</code>, that kernel's Rust metadata, and the exact rustc that produced it. Most distribution kernels are built without Rust support, and no ordinary Rust module can load on them.</p>
<p class="rv">Release CI has a second build mode for those kernels. It compiles the target kernel tree's own Rust support and ZeroFS together as LLVM bitcode, internalizes the Rust symbols, throws away unreachable support code, and pushes the resulting object through the kernel's normal module link and modpost. The finished module imports nothing but exported C symbols and loads on a kernel built with <code>CONFIG_RUST=n</code>. The build fails if any undefined Rust symbol survives the link, and CI boots such a kernel and mounts through the module, with a daily canary repeating that on the newest kernel and the newest release candidate.</p>
<p class="rv">The C objects, the module link, objtool, and modpost all use the target kernel's original C compiler and binutils; the matching Clang/LLVM tools touch only the Rust bitcode. This mode handles x86-64 kernels built with GCC or Clang; the ordinary external-module build supports little-endian arm64 as well.</p>
